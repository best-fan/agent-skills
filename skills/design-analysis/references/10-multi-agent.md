# 多 Agent 协作机制

## 定位

在**分析过程**（`02-workflow-main.md` 五步流程）与**验证过程**（`04-verification.md` 校验零到二十七）中，必要时启用多 agent / 子代理并行完成，提升速度与准确性。

**「必要时」是硬性判定，不是可选项的随意选择**：满足启用条件必须启用（保证质量），不满足条件禁止启用（避免浪费）。

---

## 一、启用判定（每次分析前必须执行）

### 启用条件（满足任一条件，必须启用多 agent）

| 判定维度 | 阈值 | 启用的原因 |
|----------|------|------------|
| 区域数量 | ≥ 5 | 第二步逐区域提取工作量大，并行分派可显著提速并降低单上下文遗漏率 |
| 表格列总数 | ≥ 8 | 逐列遍历（校验六）耗时且为最高频错误来源，独立代理可专注遍历 |
| 图表数量 | ≥ 3 | 每个图表需四子章节分析，工作量集中 |
| INSTANCE 嵌套深度 | ≥ 4 层 | MasterGo 深度遍历产生大量 DSL 数据，分派可保护主会话上下文 |
| 校验阶段异常区域数 | ≥ 2 | 需要「复核代理」独立验证修正结果，避免自我复核盲区 |
| 主会话上下文占用 | > 60% | 将数据读取下放子代理，防止主会话上下文溢出导致前文丢失 |

### 禁用条件（同时满足以下全部，禁止启用，单会话直接执行）

- 区域数量 < 5
- 无表格（或表格列 < 8）、无图表
- 无深层 INSTANCE 嵌套（< 4 层）

### 判定结果记录（必须留痕）

```markdown
### 多 Agent 启用判定

| 判定维度 | 实际值 | 阈值 | 是否触发 |
|----------|--------|------|----------|
| 区域数量 | ___ | ≥ 5 | ✅/❌ |
| 表格列总数 | ___ | ≥ 8 | ✅/❌ |
| 图表数量 | ___ | ≥ 3 | ✅/❌ |
| INSTANCE 嵌套深度 | ___ | ≥ 4 层 | ✅/❌ |

**判定结论**：启用多 agent（并行模式）/ 不启用（单会话模式）
```

> 判定在第一步「建立布局 Map」完成后立即执行——此时已获得区域数量与结构信息，可量化判定。

## 二、角色定义

| 角色 | 承担者 | 职责 | 修改文档权限 |
|------|--------|------|--------------|
| **Team Lead（总控）** | 主会话 | 建布局 Map、边界验证表、判定启用、分派任务、合并结果、统一修正、输出文档 | ✅ 唯一写入者 |
| **分析代理** `analyze-NN` | Agent 子代理 | 单区域四类内容提取（文字、图片、布局、层级）+ 图表四子章节 + 表格逐列遍历 | ❌ 只读 |
| **验证代理** `verify-NN` | Agent 子代理 | 校验组执行 / 截图交叉验证（`09-screenshot-validation.md`） | ❌ 只读 |
| **复核代理** `recheck-NN` | Agent 子代理 | 修正后复核异常区域，确认修正完整 | ❌ 只读 |

### 统一约定（与 `09-screenshot-validation.md` 保持一致）

- 使用 `Agent` 工具派发子代理；**不存在 TeamCreate 工具，禁止使用**
- 并发方式：在**同一条消息**中发出多个 `Agent` 工具调用
- 代理类型选择：只读验证用 `Explore`；需要调用 MCP 工具读取设计稿数据时用 `general-purpose`
- 🔴 **子代理一律不直接写最终文档**——所有修正统一由 Team Lead 执行，避免并发写冲突
- 后台运行的子代理回传结果使用 `SendMessage(to: "main")`；前台子代理以最终消息返回结构化结果
- 每个子代理必须**实际调用工具读取设计稿数据**，禁止凭主会话转述的摘要进行分析或验证

## 三、分析阶段多 Agent 流程（融入 `02-workflow-main.md`）

### 步骤归属表（哪些必须 Team Lead 做，哪些可分派）

| 步骤 | 执行者 | 原因 |
|------|--------|------|
| 第一步：建立布局 Map + 区域边界验证表 | 🔴 必须 Team Lead | 边界表是所有归属判断的唯一依据，必须单一来源、一次成型 |
| 第二步：区域与元素提取 | ✅ 分派 `analyze-NN` | 区域间相互独立，天然可并行 |
| 第三步：样式规范汇总 | ✅ 并入各 `analyze-NN` | 各代理返回本区域样式 token，Team Lead 汇总去重 |
| 第四步：输出文档 | 🔴 必须 Team Lead | 统一序号、统一模板、避免格式冲突 |
| 第五步：区域检查与对比完善 | ✅ 分派 `verify-NN` | 按区域对比检查可并行 |

### 分派流程

```
1. Team Lead 完成第一步 → 产出：区域列表 + 边界验证表 + 区域序号映射
2. 执行启用判定（见第一章）
3. 启用 → 制定「任务分派表」
4. 同一条消息并行派发所有 analyze-NN
5. 等待全部返回，核对返回完整性（每个区域四类内容齐全）
6. Team Lead 合并结果 → 执行第四步输出文档
```

### 任务分派表模板

```markdown
### 任务分派表

| 代理 | 区域 | 区域节点 ID | 边界（x / y / w / h） | 备注 |
|------|------|------------|----------------------|------|
| analyze-01 | 区域1 | ___ | ___ | 含表格，需逐列遍历 |
| analyze-02 | 区域2 | ___ | ___ | 含图表，需四子章节 |
| ... | ... | ... | ... | ... |
```

### 分析代理任务模板（prompt 必须包含的要素）

| 要素 | 说明 |
|------|------|
| 设计稿来源 | 文件路径 / fileKey+nodeId / layerId，及对应工具调用方式 |
| 区域边界值 | 本区域的 x/y/w/h 与左右边界（供归属判断，禁止代理自行推断边界） |
| 提取要求 | 四类内容 + 图表四子章节（`02-workflow-main.md`）+ 表格逐列遍历清单 |
| 读取规范 | readDepth 4+；检查 enabled/visible/checked；按 x 坐标排序 |
| 返回格式 | 按 `03-output-template.md` 区域章节格式返回结构化 markdown |
| 禁止事项 | 不虚构、不凭经验推断、不修改区域序号 |

### 结果合并规则

- 🔴 **区域序号以 Team Lead 第一步的编号为准**，子代理不得自行编号或改名
- 同一样式值（颜色/字号/圆角）在多区域出现时，由 Team Lead 汇总进「样式规范汇总」章节
- 子代理返回中发现疑似边界冲突（元素坐标跨越区域边界）→ 标注「待裁定」回传，**禁止子代理自行改边界**，由 Team Lead 依据边界验证表裁定
- 子代理返回不完整（缺层级小节、缺图表子章节）→ 打回重做，禁止 Team Lead 凭想象补齐

## 四、验证阶段多 Agent 流程（融入 `04-verification.md`）

### 校验分组（并行单元）

将校验零到二十七按数据依赖分为七组，每组派发一个验证代理：

| 校验组 | 覆盖校验项 | 验证重点 |
|--------|-----------|----------|
| A 结构组 | 零、一、二、五、七 | 区域数量、顺序、列表、子元素一致性 |
| B 文字组 | 三、四 | 标题文字一致性、模块存在性 |
| C 表格组 | 六、十八（表格部分） | 表格列系统性遍历、enabled 字段 |
| D 坐标层级组 | 八、九、十、十四、十五、十六、十七、十九、二十 | 排序、归属、层级、深度、同名、跳跃 |
| E 图表组件组 | 十一、十二、十三、二十一 | 图表类型、常见组件、结构化数量、图表格式 |
| F 平台专项组 | 二十二、二十三、二十四 | MasterGo INSTANCE 标题/内部元素、左右布局独立性 |
| G 流程合规组 | 二十五、二十六、二十七 | 边界表必填、修正完整性、头部信息 |

**分组调整规则**：

- 不满足启用条件的简单设计稿：合并为 A+B、C+D、E+F+G 三组甚至单会话全量执行
- 截图交叉验证（`09-screenshot-validation.md`）按**区域**派发 `verify-NN`，可与校验组代理**同批并行**
- 校验项分布因设计稿类型而异：F 组仅 MasterGo 必执行；无表格设计稿 C 组跳过

### 验证代理执行流程

```
步骤1: 重新获取设计稿数据
       → 禁止凭记忆或缓存数据校验（04 强制要求）

步骤2: 执行本组校验项
       → 逐项填写校验表格（04-verification.md 对应格式）

步骤3: 输出结构化验证报告
       → 每项：通过 ✅ / 异常 ❌（附证据：节点 ID、坐标、实际值 vs 文档值）

步骤4: ❌ 不直接修改文档
       → 异常清单回传 Team Lead
```

### 修正与复核闭环

```
验证代理发现异常
  → 回传异常清单（含证据）
    → Team Lead 统一修正（执行 08-error-correction.md 五步流程）
      → 派发 recheck-NN 复核该区域/该校验组
        → 复核通过 → 更新验证报告
        → 复核不通过 → 再次修正，直至通过
```

**强制规则**：

- [ ] **每条异常必须走完修正闭环，禁止「回传即视为处理」**
- [ ] **修正后必须派发复核代理，禁止 Team Lead 自我复核**
- [ ] **异常涉及多个区域时，修正必须覆盖所有关联位置**（校验二十六）

## 五、禁止行为

- ❌ 子代理并发写同一文档 → ✅ 修正统一由 Team Lead 执行
- ❌ 子代理凭主会话转述的摘要分析/验证 → ✅ 每个子代理必须实际调用工具读取数据
- ❌ 未完成第一步边界验证表就分派分析代理 → ✅ 边界表是分派前提
- ❌ 把全部 DSL 原文塞进每个子代理的 prompt → ✅ 只传区域节点 ID 与边界值，由子代理自行读取
- ❌ 子代理自行编号区域或更改区域名称 → ✅ 序号与命名以 Team Lead 第一步为准
- ❌ 忽略子代理返回的异常 → ✅ 每条异常必须走修正复核闭环
- ❌ 简单设计稿强行启用多 agent → ✅ 按启用判定执行，不满足则单会话
- ❌ 子代理返回不完整仍合并入文档 → ✅ 打回重做或 Team Lead 重新读取补齐
